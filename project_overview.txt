1. PROJECT SUMMARY & PROBLEM STATEMENT
--------------------------------------------------------------------------------
Ticket-Katon is a high-throughput, distributed booking engine engineered for
multimodal inter-district transit (Buses and River Launches) across Bangladesh.

The primary engineering challenge in transit booking systems (especially during
Eid migrations or flash sales) is the "Double-Booking Problem": two passengers 
attempting to book the exact same seat within the same millisecond. 

Ticket-Katon solves this using a two-tier hybrid data architecture:
- Layer 1 (In-Memory Concurrency): Redis handles sub-millisecond atomic seat holds 
  with ephemeral TTLs to guarantee zero race conditions.
- Layer 2 (Persistence & ACID Guarantees): PostgreSQL (via Supabase Connection 
  Pooler) provides durable records, relational constraints, and financial audit logs.

3. TECHNOLOGY STACK RATIONALE
--------------------------------------------------------------------------------
* Go (Golang) v1.22+:
  - Minimal memory footprint, native concurrency via goroutines.
  - Predictable latency critical for high-concurrency ticket locking.

* go-chi/chi v5:
  - Lightweight, idiomatic HTTP router 100% compliant with standard net/http.
  - Clean middleware composition and zero memory allocation overhead.

* PostgreSQL (Supabase Connection Pooler):
  - ACID-compliant transactional persistence.
  - JSONB support to store complex, dynamic seat layouts (e.g., bus deck vs 
    launch cabin arrangements) without schema alterations.

* pgxpool (jackc/pgx/v5):
  - High-performance native Go driver for PostgreSQL with robust connection pooling.

* Redis (Upstash Serverless Redis):
  - In-memory key-value store supporting atomic Lua scripting and native key TTLs.

* Stateless JWT & Bcrypt:
  - Token-based stateless authentication enabling horizontal scaling without 
    session replication bottlenecks.

[✔ COMPLETED] STEP 5: HIGH-CONCURRENCY SEAT LOCKING ENGINE (REDIS)
--------------------------------------------------------------------------------
- Problem Solved: Preventing partial reservations when multiple seats are requested
  at once (e.g., user wants seats A1 and A2, but another user locks A2 simultaneously).
- Atomic Multi-Seat Lua Scripting:
  * Checks all requested keys in a single atomic pass inside Redis memory.
  * If ANY seat is already taken, aborts instantly and locks zero seats.
  * If ALL seats are free, locks all keys with the user_id in the same operation.
- Ephemeral Lock Expiration (TTL):
  * Set to 5 minutes (300 seconds).
  * If the user abandons checkout, Redis automatically purges the keys, freeing 
    the seats without requiring heavy background DB polling jobs.
- Safe Release Lua Script:
  * Ensures that only the user who owns the lock can prematurely release it.
- Exposed Endpoints (Protected by JWT Auth):
  * POST /api/v1/seats/hold
  * POST /api/v1/seats/release


[⏳ UPCOMING] STEP 6: BOOKING CONFIRMATION & PAYMENT WORKFLOW
--------------------------------------------------------------------------------
- Goal: Finalize reservation and convert ephemeral Redis holds into permanent DB records.
- Implementation Plan:
  * Validate active seat lock in Redis before initiating the database write.
  * Begin PostgreSQL ACID transaction (pgx.Tx):
      1. UPDATE trip_seat_inventory SET status = 'BOOKED' WHERE trip_id AND seat_number.
      2. INSERT into bookings with a 12-character cryptographic PNR code.
      3. INSERT passenger details into tickets table.
      4. Release/delete the temporary Redis lock.
      5. COMMIT transaction (or ROLLBACK on any failure).
  * Integrate payment gateway simulation / webhook verification (bKash / Nagad).
